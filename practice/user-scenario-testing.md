## 배경과 문제

로봇 배달 서비스는 로봇 혼자가 아니라, 로봇과 웹 서비스가 함께 동작해야 완성됩니다.
하지만 기존 Sanity Test는 **기능 단위 체크리스트** 중심이었습니다.

- 개별 기능은 모두 통과해도, 실제 사용자 흐름에서 문제가 드러나는 경우가 있었습니다.
- 특히 **로봇–웹 연동 구간**의 이슈는 릴리즈 이후 CS로 발견되기 쉬웠습니다.

## 접근 방법

- **유저 시나리오 기준으로 Sanity Test 재구성** — 기능 목록이 아니라 사용자가 서비스를 이용하는 흐름을 기준으로 테스트를 다시 묶었습니다.
- **기능 명세 리뷰 프로세스 도입** — 명세 단계에서 QA가 시나리오 관점으로 리뷰해, TC와 명세 간 정합성을 높였습니다.
- **로봇–웹 연동 구간을 시나리오에 포함** — 로봇 단독 기능뿐 아니라, 웹과 주고받는 상태 변화까지 시나리오에서 확인하도록 설계했습니다.

## 결과

- 릴리즈 후 **CS 이슈 발생률 15% 이상 감소**
- 로봇–웹 연동 이슈를 릴리즈 전에 조기 발견
- 기능 중심 QA에서 **유저 시나리오 기반 QA**로 테스트 전략을 전환

## 배운 점

- **"기능이 된다"와 "사용자가 쓸 수 있다"는 다릅니다.** 기능 단위로는 모두 통과해도, 기능과 기능 사이, 로봇과 웹 사이의 연결에서 문제가 생길 수 있었습니다.
- **테스트의 기준을 사용자 흐름에 두면 우선순위가 분명해집니다.** 무엇부터 검증할지 판단할 때 "사용자가 어디서 막히는가"가 가장 명확한 기준이 되었습니다.
