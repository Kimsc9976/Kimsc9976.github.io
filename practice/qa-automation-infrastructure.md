## 배경과 문제

자율주행 SW는 같은 시나리오를 여러 번 반복해 봐야 배포해도 되는지 판단할 수 있습니다.
하지만 기존 검증은 사람이 직접 시나리오를 실행하는 방식이었습니다.

- **물리적 시간의 한계** — 사람이 돌릴 수 있는 횟수만큼만 테스트할 수 있어, 반복 검증이 제한적이었습니다.
- **환경 변화에 따른 비용 증가** — 검증 환경이나 시나리오가 바뀔 때마다 필요한 인력도 함께 늘어나는 구조였습니다.
- **사후 대응 중심** — 현장에서 이슈가 발생한 뒤에 원인을 분석하는 방식이라, 간헐적인 엣지 케이스는 재현 자체가 어려웠고 배포 전 안정성을 수치로 말하기 어려웠습니다.

## 접근 방법

검증을 **사람이 반복하는 작업**에서 **시스템이 반복하는 구조**로 바꾸는 데 집중했습니다.

### 1. HILS·시뮬레이터 연동 반복 검증 파이프라인

- HILS 시뮬레이터와 연동해 시나리오를 무인으로 반복 실행하는 **자동화 파이프라인** 설계·구축
- 기능당 **100회 이상** 반복 검증으로 통계적으로 의미 있는 데이터 확보
- 시나리오별 성공률, 자율주행률 분포, CPU 사용량 등을 리포트로 자동 정리해 **지표 기반 Pass/Fail** 판정
- 신규 기능 테스트 모듈 생성 가이드를 문서화하고, 스펙 기반 검증 항목을 100% 반영

### 2. 플랫폼 API 연동 SW 강건성 테스트

- 플랫폼 API로 로봇을 제어해, 수동으로는 불가능한 규모의 **장기 반복 스트레스 테스트**(1,000회 이상) 수행
- 가혹 조건을 반복 재현해, 상용 배포 전에 시스템이 견딜 수 있는 한계와 **안정성 마진**을 확인
- 이슈 유형별 발생 빈도를 집계해 결함 우선순위를 판단하고, 결과를 이슈 트래킹으로 연결

## 결과

- **반복 검증 리소스 약 80% 절감** — 인적 개입을 최소화해, 사람은 결과 분석과 판단에 집중할 수 있게 되었습니다.
- **배포 전 결함 선제 검출** — 강건성 테스트 인프라 가동 이후 다수의 핵심 결함과 안정성 이슈를 배포 전에 발견해 제거했습니다.
- **품질의 정량화** — 장기 반복 테스트로 시스템 정상 동작률 96%를 수치로 제시할 수 있게 되어, 지표로 배포를 판단하게 되었습니다.
- **검증 자산화** — 테스트 결과가 자동으로 쌓이면서 재현성과 추적성이 확보되었고, 기능이 늘어날 때 생기는 검증 리스크를 미리 막아 배포 주기 단축에 기여했습니다.

## 배운 점

- **자동화의 목적은 '횟수'가 아니라 '판단 근거'입니다.** 반복 횟수를 늘리는 것만으로는 부족했고, 결과를 지표로 정리해 Pass/Fail을 판단할 수 있어야 팀이 신뢰하는 검증이 되었습니다.
- **로봇 QA에서 Shift Left는 '실기체 전에 위험을 드러내는 것'입니다.** 테스트를 일찍 시작하는 것보다, HILS·시뮬레이터·API 반복 테스트로 현장에서 터질 문제를 배포 전에 드러내는 것이 중요했습니다.
- **구조로 남겨야 지속됩니다.** 가이드 문서화와 결과 축적이 있어야, 담당자가 바뀌어도 같은 기준으로 검증이 이어졌습니다.
