## 문제

자율주행 SW는 같은 시나리오를 여러 번 돌려 봐야 배포해도 되는지 말할 수 있습니다. 그런데 시험은 사람이 직접 실행했습니다.

- 반복 횟수가 사람이 낼 수 있는 시간만큼으로 묶여 있었습니다.
- 가끔 나오는 결함은 재현되기 전에 시험이 끝나곤 했습니다.
- 결과를 사람이 정리해 버전끼리 같은 기준으로 비교하기 어려웠습니다.

## 한 일

### 1. 시뮬레이터 검증도구 개발 (2024)

시나리오를 정해진 횟수만큼 자동으로 돌리고 판정하는 도구를 ROS 2 RQT 플러그인으로 만들었습니다.

- Test Set을 큐로 만들고, 반복마다 시나리오 로드 → 로봇 시작 신호 → 제한 시간 내 주행 → 결과 수집·판정 → 다음 반복
- 판정 결과를 검토하는 화면과 rosbag 리뷰 화면 구현
- 모듈 구조와 세팅·실행 가이드 문서화
- 이 실행·판정 구조를 이후 HILS 반복 시험과 도심 시뮬레이터 시험 자동화에 그대로 재사용

### 2. HILS 반복 시험 (2025 ~ 2026)

실제 로봇 컴퓨터를 붙인 HILS로 확장해, 실기체 없이 기능 시나리오를 무인 반복했습니다.

- 직진 주행, 목적지 도착·감속, 횡단보도 주행, 추락 감지 같은 기능별 Test Set을 100회 이상 반복
- 주행 경로별 자율주행률 분포와 CPU 최고 사용량을 리포트로 자동 생성
- 실패를 제품 결함과 시험 환경 문제(예: 배차 신호 미수신)로 나눠 집계. 시험 환경 실패가 성공률에 섞여 판정이 흔들리는 일을 막음
- 운행안전인증 기능을 확인하는 테스트 모듈도 같은 구조로 추가
- 새 기능 테스트 모듈을 만드는 가이드를 문서화해, 다른 사람도 같은 방식으로 시험을 추가할 수 있게 함

### 3. 플랫폼 API 강건성 테스트

주행 기능과 별개로, 운영 중 반복되는 동작을 로봇이 견디는지 확인했습니다.

- 플랫폼 API로 부팅 → 주요 토픽·서비스 확인 → 배차 → 배차 취소 → 대기 → 원격 재부팅 사이클을 버전마다 수백~천 회 반복
- 센서 연결 끊김, GNSS 끊김, 원격 접속 실패 같은 이슈를 유형별로 집계해 수정 우선순위 결정
- 수정 버전에서 같은 사이클로 재검증해, 고쳐졌는지를 반복 결과로 확인
